Ordnerstruktur

Eine Lib pro Slice × Layer

Jeder Ordner mit src/index.ts ist eine Nx-Lib, und index.ts ist ihre einzige öffentliche API. Projektname, Alias und Tags folgen aus dem Pfad. Pro Lib gibt es keine Config-Datei, das Crystal-Plugin leitet alles ab.

Tag-Schema

Vier Achsen, die mit UND verknüpft werden

Nx wendet jede Constraint an, deren Quell-Tag passt. Alle müssen den Import erlauben (UND). Innerhalb einer Constraint reicht ein passendes Ziel-Tag (ODER).

Layer-Matrix

Wer darf welchen Layer importieren?

Zeile = importierende Lib, Spalte = importierte Lib. Mit der Maus über eine Zeile, um sie hervorzuheben. Die Scope- und Feat-Regeln gelten zusätzlich, ein ✓ hier ist also notwendig, aber nicht hinreichend.

✓erlaubt ◐nur Libs aus scope:shared ·verboten

shell trägt type:feature und den Marker entry. app darf nur Libs mit entry, port oder scope:shared importieren, und davon nur Produktions-Layer. In *.spec.ts ist zusätzlich type:testing erlaubt, außer in types-Libs.

npm-Pakete pro Layer

  • ✕types: gar keine npm-Imports, also framework-frei
  • ✕@angular/common/http in utils, events, state, ui und feature. HTTP gibt es nur im api-Layer
  • ✕msw, vitest, @testing-library, playwright, @faker-js, openapi-msw in Produktions-Layern und in der App

Was Nx zusätzlich prüft

  • ✕Zyklen zwischen Libs. Ein Aufwärts-Import (api → state) meldet sich oft als „Circular dependency“
  • ✕statischer Import einer lazy geladenen Lib
  • ✕relative Imports über Lib-Grenzen und Imports aus Apps
Scope-Isolation

Slices reden nur über ihren Port

Pro Scope gibt es eine generierte Constraint: scope:<s> → eigener Scope, port, scope:shared. scope:shared darf nur shared. Nx kennt kein sameTag, deshalb erzeugt eslint.config.mjs diese Constraints aus den Tags im Graph.

Erlaubt

  • ✓checkin/state → booking/api: fremder Slice, aber über den port
  • ✓jede Domain → shared/*
  • ✓apps/client → booking/shell (entry, lazy geladen)

Verboten

  • ✕checkin/state → booking/state: Interna eines fremden Slice
  • ✕shared/types → booking/types: shared kennt keine Domain
  • ✕checkin/* → booking/generated/**: Domain-Clients haben keinen port
  • ✕apps/client → booking/ui: die App sieht nur entry, port und shared
Feature-Isolation

Geschwister-Feats nur über den feat-port

Jedes Feat ist ein eigener Ordner feat-<name>/ mit eigenen Libs. Seine Unterordner api, state und ui sind eigene Libs, damit die Layer-Matrix auch innerhalb des Feats gilt. Pro Feat gibt es eine Constraint: feat:<f> → eigenes Feat, feat:none, feat-port.

Testing & generierte Clients

Testcode und generierter Code mit eigenen Grenzen

Testing-Libs type:testing

  • ✓Specs (*.spec.ts) importieren Testing-Libs, auch aus fremden Domains
  • ✕Produktionscode → Testing-Lib, zusätzlich geblockt, weil Testing-Libs kein build haben
  • ✓Testing-Libs importieren nur types, testing und shared
  • ✕booking/testing → booking/state: das wäre ein Zyklus, weil der Spec in state testing importiert
  • ✕msw, vitest oder faker im App-Bundle: verify durchsucht den Build

OpenAPI-Clients generated

  • →pro Client: types (type:types), api und core (type:api), testing (type:testing)
  • ✓Domain-api (Port) → generierter api: der Port ist der Wrapper
  • ✓Domain-types → generierte types (types → types)
  • ✕ui → generierter api: Layer-Matrix
  • ✕generierter types-Teil → api-Teil desselben Clients
  • →committet ist nur src/index.ts, src/generated/** ist gitignored

Durchsetzung

Wer prüft was

Jede Regel wird dort geprüft, wo sie am frühesten auffällt.

bei jedem Nx-Befehl

Crystal-Plugin

Leitet Projekte und Tags aus dem Pfad ab. Bei unbekanntem Layer, Scope außerhalb der Liste oder einem Ordner, der nicht kebab-case ist, bricht der Graph ab, z.B. „did you mean booking?“

im IDE und bei nx lint

ESLint

@nx/enforce-module-boundaries mit den depConstraints, Deep-Import-Verbot, npm-Bans und die drei blueprint/*-Namensregeln. Fehlt der Projekt-Graph, baut ihn die Config selbst.

pnpm verify · CI

verify

150 Fälle gegen die echte Config. Dazu prüft es, dass es keine Config-Dateien in libs/ gibt, dass Tags zum Pfad passen und dass kein msw oder vitest im Bundle landet.

nx sync:check · CI

Sync-Generator

Hält app.routes.ts passend zu den vorhandenen Domain-Shells. nx sync repariert Abweichungen.

beim Anlegen

Generatoren

domain, layer, feat, testing, client, move, rename und remove erzeugen regelkonforme Namen und Routen von Anfang an.
